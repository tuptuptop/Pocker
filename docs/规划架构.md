## 一、核心理念：Everything is a Plugin

### 1.1 从 DeepSeek Harness 学到什么

DeepSeek Harness (`dsh`) 的核心哲学是 **"Everything is a Plugin"**：

> Every part of the product is a plugin, including the **model adapter**, the **tool registry**,
> the **session log**, and the **agent loop itself**, so every part is replaceable from configuration.
> There is no privileged core to patch: you extend dsh by **mounting a plugin beside the others**.

这意味着：

| 组件 | 传统架构 | Pocker 架构 (Everything is a Plugin) |
|------|---------|-------------------------------------|
| LLM 模型适配器 | 内置硬编码 | **Plugin** — 可替换为 OpenAI/Anthropic/Ollama/本地模型 |
| 工具注册表 | 内置固定 | **Plugin** — 工具集可动态挂载/卸载 |
| 会话日志 | 内置存储 | **Plugin** — 可替换为 SQLite/PostgreSQL/文件 |
| Agent 循环 | 核心代码 | **Plugin** — 默认实现可整体替换 |
| 沙箱执行 | 内置固定 | **Plugin** — 可替换为进程隔离/容器隔离/WASM |
| CLI / TUI / GUI | 内置固定 | **Plugin** — 界面层也可替换 |
| Skills 系统 | 内置固定 | **Plugin** — 每个 Skill 是一个独立插件 |

### 1.2 回答关键问题

#### Q1: DeepSeek Harness 里面是把 LLM 也做成 plugin 了吗？

**是的。** DSH 中 LLM 模型适配器是一个 plugin，通过 `ctx.llm` seam 挂载到共享上下文。切换模型（如从 OpenAI 切到 Ollama）只需替换模型适配器 plugin，不需要修改核心代码。具体机制：

```
插件注册: model adapter plugin → ctx.llm (Service Definition + Provider + Consumer)
使用时:   agent loop → ctx.llm.stream(messages) → 模型适配器 → HTTP API → LLM
```

Pocker 完全采纳这一设计：

```
Pocker LLM Plugin 架构:

┌─────────────────────────────────────────────┐
│              Pocker Engine                   │
│  (无特权核心，只是插件组合的运行时)            │
│                                              │
│  ctx.llm seam ←─── LLM Adapter Plugin       │
│  ctx.tools seam ←── Tool Registry Plugin    │
│  ctx.session seam ←── Session Log Plugin    │
│  ctx.sandbox seam ←── Sandbox Plugin        │
│  ctx.skills seam ←── Skills Registry Plugin │
│                                              │
│  可替换的 LLM 适配器:                         │
│  ├── @pocker/llm-openai     (GPT 系列)      │
│  ├── @pocker/llm-anthropic  (Claude 系列)    │
│  ├── @pocker/llm-deepseek   (DeepSeek 系列)  │
│  ├── @pocker/llm-ollama     (本地模型)       │
│  ├── @pocker/llm-gemini     (Gemini 系列)    │
│  └── @pocker/llm-custom     (自定义适配)     │
└─────────────────────────────────────────────┘
```

#### Q2: Skills 怎么也形成为 plugin？

在 DSH 中，**seam（能力缝隙）**是可替换的能力接缝点。Skills 天然适合做成 plugin——每个 Skill 声明自己的输入 schema、输出 schema 和执行逻辑，通过 `ctx.tools` 或独立的 `ctx.skills` seam 注册：

```
Skill Plugin 架构:

┌──────────────────────────────────────────────┐
│           Skills Registry Plugin             │
│           (管理所有 skill plugin)              │
│                                              │
│  ├── @pocker/skill-code-review              │
│  │   input:  { code: string, language: string } │
│  │   output: { issues: Issue[], score: number } │
│  │   impl:   ctx.llm.analyze(code) + rules   │
│  │                                            │
│  ├── @pocker/skill-doc-generator            │
│  │   input:  { source: string, format: string } │
│  │   output: { docs: string }                 │
│  │   impl:   parse(source) + ctx.llm.generate() │
│  │                                            │
│  ├── @pocker/skill-data-analysis            │
│  │   input:  { data: any, query: string }    │
│  │   output: { insights: string[], charts: any } │
│  │   impl:   analyze(data) + ctx.llm.reason() │
│  │                                            │
│  └── @pocker/skill-file-converter           │
│      input:  { file: Buffer, target: string } │
│      output: { result: Buffer }              │
│      impl:   convert(file, target)           │
│      (纯工具型 skill，不需要 LLM)             │
└──────────────────────────────────────────────┘

Skill Plugin 的三种角色:
  1. Service Definition — 声明 skill 接口 (input/output schema)
  2. Service Provider   — 实现 skill 逻辑 (可调用 ctx.llm, ctx.tools 等)
  3. Consumer           — 其他 plugin 可通过 ctx.skills.invoke() 调用
```

### 1.3 Pocker 的设计哲学

```
Pocker 三大设计原则:

1. Everything is a Plugin
   ─── 没有特权核心，一切皆可替换
   ─── LLM 是 plugin，Skill 是 plugin，沙箱是 plugin，UI 也是 plugin
   ─── 通过 mount/unmount 插件来扩展或替换功能

2. Composition over Configuration
   ─── 通过 Profiles + Bundles 有序分层组合
   ─── 上层 bundle 的 patch 可以覆盖下层
   ─── 不是配置文件，而是代码+配置的分层叠加

3. Seams as Extension Points
   ─── 每个能力是一个 seam (ctx.llm, ctx.tools, ctx.sandbox...)
   ─── 插件通过注册到 seam 来贡献能力
   ─── 卸载插件时，注册自动 unwind (可逆效应)
```

## 三、Profiles 和 Bundles

### 3.1 Profile 设计

参考 DSH 的 Profile 机制——一个 Profile 是命名的插件组合配置，列出它堆叠的 bundles、安装的 out-of-tree 插件、用户的 patch。

```yaml
# ~/.pocker/profiles/web/profile.yaml
# Web UI Profile — 完整的浏览器界面体验

name: web
description: "Pocker with Web UI — full browser experience"
template: true  # 可作为模板被复制

bundles:
  - @pocker/core-bundle        # 基础层: model adapter, tools, session, sandbox
  - @pocker/llm-bundle         # LLM 层: OpenAI, Anthropic, Ollama 适配器
  - @pocker/tools-bundle       # 工具层: shell, fs, http, git
  - @pocker/skills-bundle      # 技能层: code-review, doc-gen, data-analysis
  - @pocker/web-bundle         # Web 层: React UI + API Server + WebSocket

plugins:
  # out-of-tree 插件 (用户安装的)
  - @user/my-custom-skill:1.2.0
  - @user/my-llm-adapter:0.1.0

# 用户的自定义 patch (覆盖上层配置)
patch:
  config:
    llm:
      default_model: "deepseek-chat"
      fallback_model: "ollama/llama3"
    sandbox:
      mode: "strict"
      timeout: 30000
    approval:
      shell: "manual"        # shell 命令需要手动审批
      fs_write: "allowlist"  # 文件写入需要白名单
```

```yaml
# ~/.pocker/profiles/headless/profile.yaml
# Headless Profile — 无界面，纯 API 模式

name: headless
description: "Pocker without UI — API only mode"

bundles:

  - @pocker/llm-bundle
```

### 3.2 Bundle 设计

Bundle 是 Cordis 配置行的分发格式——它插入的代码和配置保持可被上层 patch 覆盖。

```
Bundle 结构:

@pocker/core-bundle/
├── package.json          # dsh.bundle 字段指向 patch 文件
├── cordis.patch.yml      # Cordis 配置行 (定义要 mount 的插件)
├── src/
│   ├── model-adapter/    # LLM 适配器插件
│   ├── tool-registry/    # 工具注册表插件
│   ├── session-log/      # 会话日志插件
│   ├── sandbox/          # 沙箱插件
│   └── approval/         # 审批插件
└── README.md
```

```yaml
# @pocker/core-bundle/cordis.patch.yml
# 定义此 bundle mount 的插件和配置行

config:
  # LLM 适配器 seam
  - id: llm-openai
    plugin: ./src/model-adapter/openai
    provides: ctx.llm
    config:
      api_key: ${env:OPENAI_API_KEY}
      default_model: gpt-4o

  - id: llm-ollama
    plugin: ./src/model-adapter/ollama
    provides: ctx.llm
    config:
      host: http://localhost:11434
      default_model: llama3

  # 工具注册表 seam
  - id: tool-registry
    plugin: ./src/tool-registry
    provides: ctx.tools

  # 会话日志 seam
  - id: session-sqlite
    plugin: ./src/session-log/sqlite
    provides: ctx.session
    config:
      path: ~/.pocker/sessions.db

  # 沙箱 seam
  - id: sandbox-process
    plugin: ./src/sandbox/process
    provides: ctx.sandbox
    config:
      mode: strict
      timeout: 30000

  # 审批 seam
  - id: approval-default
    plugin: ./src/approval
    provides: ctx.approval
    config:
      shell: manual
      fs_write: allowlist
```

### 3.3 插件树组合顺序

```
启动时的插件树组合 (从下到上有序应用):

Layer 0: @pocker/core-bundle     ← 基础层 (LLM/tools/session/sandbox)
    ↓ mount
Layer 1: @pocker/llm-bundle      ← LLM 层 (额外模型适配器)
    ↓ mount
Layer 2: @pocker/tools-bundle    ← 工具层 (额外工具)
    ↓ mount
Layer 3: @pocker/skills-bundle   ← 技能层 (skill 插件)
    ↓ mount
Layer 4: @pocker/web-bundle      ← 界面层 (Web UI)
    ↓ mount
Layer 5: 用户 cordis.patch.yml   ← 用户覆盖层 (最高优先级)
    ↓
  最终运行的插件树

每层都是 patchable 的:
  - 上层可以替换下层插入的整行配置
  - 上层可以插入新的配置行
  - 卸载插件时，其注册自动 unwind (可逆效应)

查看当前插件树:
  pocker --profile web --dump-config
```

## 四、Seam 设计（能力接缝点）

### 4.1 核心 Seam 列表

参考 DSH 的 extension cookbook，每个 seam 是一个可替换的能力接缝点：

| Seam | Context Key | 说明 | 默认实现 | 可替换为 |
|------|------------|------|---------|---------|
| LLM 适配器 | `ctx.llm` | 大语言模型调用 | OpenAI 适配器 | Anthropic/Ollama/DeepSeek/自定义 |
| 工具注册表 | `ctx.tools` | 工具注册和执行 | 本地工具集 | 远程工具/MCP 工具/自定义 |
| 技能注册表 | `ctx.skills` | Skill 注册和调用 | 内置技能集 | 自定义技能/社区技能 |
| 会话日志 | `ctx.session` | 对话历史和事件 | SQLite | PostgreSQL/文件/内存 |
| 沙箱 | `ctx.sandbox` | 代码执行隔离 | 进程隔离 | 容器/WASM/E2B |
| 审批 | `ctx.approval` | 操作审批策略 | 手动审批 | 自动/白名单/策略引擎 |
| 文件系统 | `ctx.fs` | 文件访问 | 本地 FS | 远程 FS/虚拟 FS |
| 终端 | `ctx.terminal` | 终端管理 | 本地 PTY | 远程 PTY/SSH |
| 事件总线 | `ctx.bus` | 事件发布订阅 | 内部总线 | NATS/Redis |
| 凭证 | `ctx.credentials` | 密钥管理 | 文件存储 | Vault/OS Keychain |
| 遥测 | `ctx.metrics` | 指标收集 | 本地收集 | Prometheus/Datadog |
| 配置 | `ctx.config` | 配置管理 | YAML 文件 | Env/Consul/etcd |

### 4.2 LLM Seam 详细设计

```typescript
// ctx.llm seam — LLM 适配器接口
// 参考 DSH 的 llm/stream 事件和 agent/request 事件

interface LLMSeam {
  // 流式生成 (核心方法)
  stream(messages: Message[], options?: LLMOptions): AsyncIterable<Chunk>;

  // 非流式生成
  generate(messages: Message[], options?: LLMOptions): Promise<Response>;

  // 嵌入向量
  embed(text: string): Promise<number[]>;

  // 模型信息
  models(): ModelInfo[];

  // 能力声明
  capabilities(): LLMCapabilities;
}

interface LLMOptions {
  model?: string;
  temperature?: number;
  max_tokens?: number;
  tools?: ToolDefinition[];      // function calling
  stream?: boolean;
  signal?: AbortSignal;
}

interface Chunk {
  type: 'text' | 'tool_call' | 'tool_result' | 'done' | 'error';
  content?: string;
  tool_call?: { id: string; name: string; args: any };
  usage?: { input_tokens: number; output_tokens: number };
}

// LLM 适配器插件实现示例
class OpenAIAdapterPlugin implements Plugin {
  name = '@pocker/llm-openai';

  mount(ctx: Context) {
    // 注册到 ctx.llm seam
    ctx.llm.register({
      name: 'openai',
      stream: async function* (messages, options) {
        const response = await fetch('https://api.openai.com/v1/chat/completions', {
          method: 'POST',
          headers: { 'Authorization': `Bearer ${ctx.credentials.get('OPENAI_API_KEY')}` },
          body: JSON.stringify({ model: options.model, messages, stream: true })
        });
        // 解析 SSE 流并 yield chunks
        for await (const chunk of parseSSE(response.body)) {
          yield chunk;
        }
      },
      models: () => [
        { id: 'gpt-4o', name: 'GPT-4o', context_window: 128000 },
        { id: 'gpt-4o-mini', name: 'GPT-4o Mini', context_window: 128000 }
      ],
      capabilities: () => ({
        function_calling: true,
        vision: true,
        streaming: true
      })
    });
  }

  unmount(ctx: Context) {
    // 可逆效应: 卸载时自动移除注册
    ctx.llm.unregister('openai');
  }
}
```

### 4.3 Skills Seam 详细设计

```typescript
// ctx.skills seam — 技能注册表接口

interface SkillsSeam {
  // 注册技能
  register(skill: SkillDefinition): void;
  unregister(name: string): void;

  // 调用技能
  invoke(name: string, input: any): Promise<SkillResult>;

  // 列出所有技能
  list(): SkillInfo[];

  // 搜索技能
  search(query: string): SkillInfo[];

  // 安装/卸载技能 (从 Hub)
  install(name: string, version?: string): Promise<void>;
  uninstall(name: string): Promise<void>;
}

interface SkillDefinition {
  name: string;
  version: string;
  description: string;

  // 输入/输出 schema (JSON Schema)
  input_schema: JSONSchema;
  output_schema: JSONSchema;

  // 技能类型
  type: 'llm' | 'tool' | 'hybrid';
  // llm:    需要 LLM 能力 (调用 ctx.llm)
  // tool:   纯工具型 (不需要 LLM)
  // hybrid: 混合型 (工具 + LLM)

  // 执行函数
  execute: (input: any, ctx: Context) => Promise<any>;

  // 依赖声明
  requires?: string[];  // 需要的 seam (如 ['ctx.llm', 'ctx.tools'])
}

// Skill Plugin 实现示例
class CodeReviewSkillPlugin implements Plugin {
  name = '@pocker/skill-code-review';

  mount(ctx: Context) {
    ctx.skills.register({
      name: 'code-review',
      version: '1.0.0',
      description: 'AI-powered code review with rule checks',

      input_schema: {
        type: 'object',
        properties: {
          code: { type: 'string' },
          language: { type: 'string', enum: ['js', 'ts', 'py', 'go', 'rust'] }
        },
        required: ['code', 'language']
      },

      output_schema: {
        type: 'object',
        properties: {
          issues: { type: 'array', items: { type: 'object' } },
          score: { type: 'number', minimum: 0, maximum: 100 },
          summary: { type: 'string' }
        }
      },

      type: 'hybrid',  // 混合型: 规则检查 + LLM 分析

      requires: ['ctx.llm'],

      execute: async (input, ctx) => {
        // 1. 规则检查 (工具型)
        const ruleIssues = runLintRules(input.code, input.language);

        // 2. LLM 深度分析 (LLM 型)
        const llmAnalysis = await ctx.llm.generate([{
          role: 'user',
          content: `Review this ${input.language} code:\n${input.code}`
        }]);

        return {
          issues: [...ruleIssues, ...parseLLMIssues(llmAnalysis)],
          score: calculateScore(ruleIssues, llmAnalysis),
          summary: llmAnalysis.content
        };
      }
    });
  }

  unmount(ctx: Context) {
    ctx.skills.unregister('code-review');
  }
}
```

## 五、Turn Flow（Agent 循环）

### 5.1 事件驱动的 Turn 生命周期

参考 DSH 的 turn flow 设计——一个 step 是一次模型请求 + 工具调用，一个 turn 是零或多个 step：

```
turn/start
  │
  ▼
claim next-step input + one queued message
assemble prompt sections + tool schemas
  │
  ├──► agent/pre-step          (waterfall: 可重写/拒绝 claimed messages)
  │         │
  │         ▼
  │    reject, or first enter rewritten empty → close turn with no step
  │         │
  │         ▼
  │    step/start
  │         │
  │         ▼
  │    agent/request ──► llm/stream ──► assistant/message  (waterfall)
  │         │                                      │
  │         │                                      ▼
  │         │                              tool/call*
  │         │                                      │
  │         ▼                                      ▼
  │    tools/pre-execute ──► tools/execute ──► tools/post-execute
  │                                              │
  │                                              ▼
  │                                         tool/result*
  │                                              │
  │    step/end                                 │
  │         │                                   │
  │         ▼                                   │
  │    tools owe another request, or next-step input arrived
  │         │                                   │
  │         └───► claim ───► next step          │
  │                                              │
  └──► agent/turn-stopping (serial, no next())  │
                                                 │
turn/end ◄──────────────────────────────────────┘

事件类型:
  ─── Durable (持久化到会话日志): turn/*, step/*, user/message, assistant/message, tool/*
  ─── Live (实时扩展点): agent/pre-step, agent/request, llm/stream, tools/*
```

### 5.2 事件 Map

```typescript
// 事件生产者和消费者映射

const EventMap = {
  // Durable 事件 (持久化到会话日志)
  'turn/start':           { producers: ['agent-loop'],  consumers: ['session-log', 'ui'] },
  'turn/end':             { producers: ['agent-loop'],  consumers: ['session-log', 'ui'] },
  'step/start':           { producers: ['agent-loop'],  consumers: ['session-log', 'ui'] },
  'step/end':             { producers: ['agent-loop'],  consumers: ['session-log', 'ui'] },
  'user/message':         { producers: ['ui', 'api'],   consumers: ['session-log', 'agent-loop'] },
  'assistant/message':    { producers: ['llm'],         consumers: ['session-log', 'ui'] },
  'tool/call':            { producers: ['llm'],         consumers: ['session-log', 'tools', 'ui'] },
  'tool/result':          { producers: ['tools'],       consumers: ['session-log', 'llm', 'ui'] },

  // Live 事件 (实时扩展点，waterfall)
  'agent/pre-step':       { producers: ['agent-loop'],  consumers: ['approval', 'policy', 'context'] },
  'agent/request':        { producers: ['agent-loop'],  consumers: ['llm', 'context-injector'] },
  'llm/stream':           { producers: ['llm'],         consumers: ['context-filter', 'telemetry'] },
  'tools/pre-execute':    { producers: ['tools'],       consumers: ['approval', 'policy'] },
  'tools/post-execute':   { producers: ['tools'],       consumers: ['telemetry', 'audit'] },
  'agent/turn-stopping':  { producers: ['agent-loop'],  consumers: ['ui', 'cleanup'] },

  // Capability 事件 (附加策略和适配器)
  'fs/*':                 { producers: ['fs-plugin'],      consumers: ['policy', 'audit'] },
  'tools/*':              { producers: ['tools-plugin'],   consumers: ['policy', 'audit'] },
  'telemetry/*':          { producers: ['telemetry-plugin'], consumers: ['metrics', 'ui'] },
};
```

| **样式** | **TailwindCSS 4** | Hermes-Studio 使用，快速开发 |

| **本地存储** | **better-sqlite3** | Hermes-Studio 使用，同步高性能 |
| **缓存** | **ioredis** | Hermes-Studio 使用，优雅降级 |
| **WebSocket** | **ws** | Hermes-Studio 使用 |
| **代码高亮** | **Shiki** | Hermes-Studio 使用 |
| **Schema** | **Zod** | Hermes-Studio 使用，类型安全 |
| **构建** | **Vite + tsup** | Hermes-Studio 使用 Vite，tsup 打包库 |
| **Hub 后端** | **Go** | 高并发 Web 服务 |
| **Hub 搜索** | **Meilisearch** | 轻量高性能搜索 |
| **Hub 存储公告** | **PostgreSQL + MinIO** | 可靠关系型 + S3 兼容对象存储 |
| **安全扫描** | **Trivy + npm audit** | 漏洞扫描 |
| **CI/CD** | **GitHub Actions** | 自动化构建发布 |

### 10.2 为什么不用 Rust？

| 上一版方案 (Rust) | 当前方案 (Node.js/TypeScript) | 理由 |
|---|---|---|
| Engine 用 Rust | Engine 用 TypeScript | DSH 和 Hermes-Studio 都是 TS，生态一致 |
| 高性能但开发慢 | 性能足够，开发快 | 插件系统 IO 密集而非 CPU 密集 |
| 跨平台编译复杂 | Node.js 天生跨平台 | npm/npx 一键安装 |
| 学习曲线陡峭 | TS 生态开发者众多 | 社区贡献门槛低 |
| 原生隔离需要 native addon | 通过 child_process + 平台抽象 | 实用优先 |

**决策**: 全面采用 TypeScript + Node.js，与 DSH 和 Hermes-Studio 生态统一，确保跨平台快速安装和开发效率。

### 11.2 审批系统（参考 Hermes-Studio）

```yaml
# 审批策略配置
approval:
  # Shell 命令审批
  shell:
    mode: manual  # manual | allowlist | auto
    allowlist:
      - "ls *"
      - "cat *"
      - "git status"
    denylist:
      - "rm -rf *"
      - "sudo *"

  # 文件系统操作审批
  fs:
    write:
      mode: allowlist  # manual | allowlist | auto
      allowlist:
        - "/tmp/*"
        - "./workspace/*"
    read:
      mode: auto  # 读取默认自动允许

  # 网络请求审批
  network:
    mode: allowlist
    allowlist:
      - "https://api.openai.com/*"
      - "https://api.anthropic.com/*"
      - "http://localhost:*"

  # 审批 UI (Web/TUI)
  ui:
    - 显示完整命令和参数
    - 显示上下文 (哪个插件/工具触发的)
    - 三个选项: Approve / Deny / Always Allow
    - 审批历史记录
```

## 十三、关键设计决策

### 13.1 为什么选择 TypeScript 而非 Rust？

| 考量 | TypeScript | Rust |
|------|-----------|------|
| 与 DSH 一致性 | 完全一致 (DSH 是 TS) | 不一致 |
| 与 Hermes-Studio 一致性 | 完全一致 (HS 是 TS) | 不一致 |
| 跨平台安装 | npx 一键运行 | 需编译/下载二进制 |
| 插件开发门槛 | 低 (TS 开发者众多) | 高 (学习曲线陡) |
| 性能 | 足够 (IO 密集场景) | 更优 (CPU 密集场景) |
| 生态 (npm) | 最丰富 | 有限 |
| Cordis 框架 | 原生支持 | 需重写 |

**决策**: TypeScript——与 DSH 和 Hermes-Studio 生态统一，确保 npx 零安装运行，降低插件开发门槛。

### 13.2 为什么基于 Hermes-Studio 开发 UI？

| 考量 | Hermes-Studio | 从零开发 |
|------|--------------|---------|
| 功能完整度 | 30+ 特性已验证 | 需重新实现 |
| 技术栈 | React+TanStack+Zustand (成熟) | 需选型 |
| 终端集成 | xterm 已集成 | 需集成 |
| 审批系统 | 已实现 | 需实现 |
| 多 Agent | 已实现 | 需实现 |
| PWA | 已实现 | 需实现 |
| 测试覆盖 | 199 测试通过 | 需编写 |

**决策**: 基于 Hermes-Studio 的技术栈和架构模式开发 UI，复用其验证过的设计模式和依赖库。

### 13.3 为什么采纳 "Everything is a Plugin"？

| 考量 | 传统架构 | Everything is a Plugin |
|------|---------|----------------------|
| 可扩展性 | 需修改核心代码 | mount 插件即可 |
| 可替换性 | 核心组件不可替换 | 一切可替换 |
| 社区贡献 | 需 fork 仓库 | 写插件即可 |
| 定制化 | 需重新编译 | Profile + Patch |
| 测试隔离 | 困难 | 替换插件为 mock |

**决策**: 采纳 DSH 的 "Everything is a Plugin"——没有特权核心，所有组件（LLM、工具、沙箱、UI、Skills）都是可替换的插件。

## 十五、总结

1. **DeepSeek Harness** — "Everything is a Plugin" 架构哲学

   - Hub 平台：搜索/发现/评分/版本管理/安全审计
   - 插件包格式：标准化打包 + 签名 + 分发

3. **Hermes-Studio** — UI 技术栈和功能参考
   - React + TanStack + Zustand + TailwindCSS + xterm
   - 30+ 验证过的功能特性（审批/多 Agent/Cron/知识图谱/PWA）
   - SSE 流式 + WebSocket 实时通信
